## Design notes

- Followed A3's module tree and canonical-type shapes exactly (`Tool`,
  `ToolCall`, `LLMProvider.run(prompt, tools, history)`). `Message` and
  `LLMResponse` are referenced by A3's snippet but not spelled out
  field-by-field; defined the minimal obvious shape for each (role/
  content/tool_call_id/name for `Message`; text + tool_calls for
  `LLMResponse`) — implementation-level filling-in, not a redesign of
  A3's boundary.
- `LLMProvider.run` and the tool functions in `tools.py` are `async`
  (tools need to await the async DB session; A3 explicitly calls the
  tools "plain async function[s]"). The provider adapters' own SDK
  calls are synchronous (both OpenAI's and Gemini's Python SDKs are
  sync), so `engine.py` calls `provider.run(...)` via
  `starlette.concurrency.run_in_threadpool` — same pattern
  `app/gateway/router.py` already uses for Plaid's blocking SDK.
- OpenAI's wire format requires a `tool_call_id` correlating a tool
  result back to the call that requested it; the canonical `ToolCall`
  (per A3) deliberately doesn't carry one. Resolved entirely inside
  `openai_provider.py`: it caches the last turn's raw `id`s (keyed by
  tool name) and reconstructs the correlated `tool_calls`/
  `tool_call_id` fields when rendering history back to OpenAI's
  format. Invisible to `engine.py`/`tools.py`, consistent with A3's
  "only the adapters know about wire formats" intent. Known
  simplification: this only guarantees correct reconstruction for the
  most recently completed tool-call turn, not arbitrarily deep
  multi-round history — acceptable given the three tools here rarely
  need more than one round trip, but noted here rather than silently
  assumed.
- `run_weekly_triage` does not expose the read-only tools to Gemini —
  per A3's own reasoning ("leaning on the larger context window to
  reason over a fuller week of data at once rather than needing to
  pre-summarize before handing it to the model"), the caller-supplied
  `transactions`/`accounts` are serialized directly into the prompt
  instead.

## Notes / assumptions (not spec deviations, but flagged for visibility)

- **`get_account_summary`'s "balance"**: A1's `CreditAccount` schema
  has no stored balance column, and A2's `BankConnector` Protocol has
  no live-balance fetch method — there is currently no source of truth
  for a real account balance anywhere in the system. `current_balance`
  is computed in `app/domains/finance/service.py::get_account_summary`
  as the sum of non-pending transaction amounts per account (Plaid's
  own sign convention: positive = debit/purchase, negative = credit/
  refund/payment). This is a reasonable reading of A3's "balance ...
  per CreditAccount" given what's actually stored, not a redesign of
  A1's schema — but if the intent was a real-time Plaid balance call
  instead, that needs its own Architect ticket (new `BankConnector`
  method + likely a schema change), not something to guess into
  existence here.
- **`google-generativeai`** (the SDK named in the ticket / likely by
  R3) emits a `FutureWarning` on import: Google has ended support for
  it in favor of a new `google-genai` package. Used it anyway since
  it's what was named in scope for this ticket; worth a DevOps/
  Architect follow-up ticket to migrate before it's actually removed,
  not urgent for a personal project right now.
