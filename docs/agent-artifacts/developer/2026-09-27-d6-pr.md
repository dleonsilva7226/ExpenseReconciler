## Design notes

- **`DigestLog`** (`app/domains/finance/models.py`): exactly the four
  columns A4 specifies (`id`, `sent_at`, `period_start`,
  `period_end`), reusing `UUIDPrimaryKeyMixin` per the mixin's own
  comment anticipating this. Deliberately does **not** use
  `TimestampMixin` — A4 doesn't call for `created_at`/`updated_at` on
  this table, so I didn't add columns A4 didn't ask for. Added a
  `UniqueConstraint` on `period_end` as a DB-level backstop for the
  same idempotency guarantee A4 requires (protects against a race
  between the application-level check and insert) — this is
  additive robustness, not a new column or a design change, in the
  same spirit as A1's `provider_transaction_id` uniqueness.
- **Period definition:** "past 7 days" (A4 step 1) is computed as
  `[today - 7 days, today]`, with `period_end = today` doubling as the
  `DigestLog` idempotency key — an implementation-level choice A4
  leaves to Developer (it doesn't pin down calendar weeks vs. a
  rolling 7-day window).
- **Utilization flagging:** `finance_service.get_account_summary`
  (D5) already computes a raw `utilization` ratio; `weekly_finance_audit.py`
  adds an `over_utilization_threshold` boolean per account at the 30%
  threshold A4 confirms, before handing accounts to
  `run_weekly_triage`. This satisfies A4's "flagging any account over
  30%" without changing `agent.engine.run_weekly_triage`'s signature
  (D5's, already merged) — the threshold judgment is computed here,
  in the job, not left to the model or bolted onto `engine.py`.
- **Telegram length limit (R2/A4):** `run_weekly_triage`'s prompt
  (D5's, unchanged) already instructs Gemini to produce a bounded,
  concise summary — A4's preferred primary fix for overflow. On top of
  that, `_fit_to_telegram_limit` hard-truncates to 4,096 chars as a
  defensive backstop so a request can never reach the Bot API
  oversized regardless of what the model actually returns. This is a
  safety net alongside the prompt-level strategy A4 names, not a
  substitute for it.
- **Sending:** `python-telegram-bot`'s async `Bot.send_message`,
  per R2's explicit library recommendation. Added to
  `requirements.txt` under its own D6 section — it was already
  anticipated in the file's top-of-file comment listing deps ticket
  PRs would add "as they land," so this isn't inventing an
  unnamed dependency.
- **Trigger endpoint auth:** `POST /jobs/weekly-digest/trigger` reads
  `Authorization: Bearer <JOBS_TRIGGER_SECRET>` and compares via
  `secrets.compare_digest`, per A4/R4 ("a bearer token ... compared
  via `secrets.compare_digest`, not the admin Basic Auth"). Placed in
  `app/gateway/router.py` alongside A2's other endpoints, per A4's
  explicit instruction.
- **Idempotency in the endpoint:** the endpoint itself has no extra
  logic beyond auth + calling `run_weekly_digest(session)` — the
  idempotency check lives entirely inside the job function (checks
  `DigestLog` before doing anything else: no transaction query, no
  model call, no Telegram send, no commit), so a duplicate trigger for
  an already-sent period returns 200 with `{"sent": false, ...}`
  cheaply.

## Notes / assumptions (not spec deviations, but flagged for visibility)

- A4 doesn't name an exact module path for the job logic itself (only
  the trigger endpoint's path is spelled out). Used
  `app/jobs/weekly_finance_audit.py`, matching both `PLAN.md`'s
  original file tree and the ticket tracker's filename — cross-checked
  against A4 rather than assumed, since the ticket said not to treat
  the tracker as authoritative over the spec.
- Transaction serialization for the LLM prompt (`_serialize_transaction`)
  passes `Decimal`/`date` fields through as-is (not pre-stringified) —
  consistent with `engine.py`'s own `_json_default` handling of those
  types (D5), so no double-encoding.
